# GovProxy — Phase 3 Design Document

**Phase 3: Aggregation Engine + AI-Generated Summaries**

Status: DRAFT FOR DISCUSSION | Version 0.1 — May 2026

> This document describes Phase 3 in detail so we can discuss, refine, and then turn it into GitHub issues with acceptance criteria. Built tier-aware from the start, since all developers are git-only at launch.

---

## 1. Phase 3 Goal

Phase 1 collects daily snapshots. Phase 2 displays them through the dashboard, computing views on the fly from daily data. Phase 3 adds two things:

1. **The aggregation engine** — pre-computed weekly, monthly, quarterly, and yearly rollups so the dashboard stays fast as history grows, deltas are available for trend comparisons, and the AI maturity score is computed and tracked over time.

2. **AI-generated summaries** — automated narrative reports at all four levels (weekly, monthly, quarterly, yearly) that turn aggregate numbers into the readable story a manager hands to their VP, generated by a configurable model defaulting to local.

**Critical context for Phase 3:** every developer is git-only (MEDIUM tier) at launch. So aggregates and summaries must describe git-derived signals honestly and avoid implying direct-usage data that doesn't exist. Tier-awareness threads through everything in this phase.

**Duration estimate:** 2–3 weeks (refine once scope locks).

---

## 2. Why Pre-Computed Aggregates Now

In Phase 2, dashboard endpoints query daily snapshots and aggregate in-query. That's fine at launch scale. But three things push us to pre-compute:

- **Performance over time.** As months of daily data accumulate across developers and tools, on-the-fly aggregation for long ranges (year, lifetime) gets slow. Pre-computed rollups keep the dashboard instant.
- **Deltas need a prior period.** "Acceptance rate up 8% vs last month" requires a stored previous-period value to compare against. Aggregates are where deltas live.
- **Summaries need stable inputs.** The AI summaries narrate aggregates. Generating a monthly summary from a fixed monthly_aggregate row (rather than re-querying raw data each time) makes summaries reproducible and cheap.

The aggregation tables were already defined in the V1 schema (weekly_aggregates, monthly_aggregates, quarterly_aggregates). Phase 3 implements the jobs that populate them, adds yearly, and adds the maturity score and delta columns.

## 3. The Aggregation Engine

### 3.1 Rollup Hierarchy

```
daily snapshots (raw)
  → weekly_aggregates    (computed every Monday for the prior week)
  → monthly_aggregates   (computed on the 1st for the prior month)
  → quarterly_aggregates (computed at quarter boundary for the prior quarter)
  → yearly_aggregates    (computed Jan 1 for the prior year)
```

Each level can be computed from the level below it (monthly from weekly, etc.) OR from daily — computing from daily is simpler and avoids compounding rounding, so we compute every level from daily snapshots directly. At this data scale the cost is trivial.

### 3.2 What Each Aggregate Stores

Per developer per period (weekly, monthly) and per team per period (quarterly, yearly):

**Git-derived metrics (the real data at launch):**
- Active days (days with any commit or AI signal)
- Total commits, lines added/removed, files changed
- PRs opened, merged, avg time-to-merge
- Review comments given
- Average code churn rate
- Average AI signature score (labeled estimated)
- Commit burst count

**Cost metrics (from expense data):**
- Subscription cost for the period
- Cost per PR, cost per active day (cost-per-outcome)

**Tool-usage metrics (mostly null at launch, populated as connectors come online):**
- Interaction count, acceptance rate, features used — stored as nullable, so the schema is ready when HIGH-tier data arrives without migration

**Computed:**
- Data quality tier for the developer in that period (high/medium/low)
- AI maturity score (see Section 4)
- Deltas vs previous period for key metrics

### 3.3 Delta Calculation

Each aggregate stores the change from the previous comparable period:

```
commit_velocity_delta_pct = (this_period_commits - prev_period_commits)
                            / max(prev_period_commits, 1) * 100
churn_rate_delta          = this_period_churn - prev_period_churn
ai_signature_delta        = this_period_signature - prev_period_signature
cost_per_pr_delta_pct     = ...
```

Deltas power the "up 8% vs last month" language in both the dashboard and the summaries. When there's no prior period (first week of data), deltas are null and the UI/summary says "first period — no comparison yet" rather than showing a fake 0%.

### 3.4 Scheduling

node-cron jobs at period boundaries:
- Weekly: Monday 04:00 UTC for the prior week
- Monthly: 1st 04:30 UTC for the prior month
- Quarterly: quarter start 05:00 UTC
- Yearly: Jan 1 05:00 UTC

Each job is idempotent — re-running for a period recomputes and overwrites that period's aggregate from immutable daily data, so a re-run is always safe. A manual CLI trigger (`govproxy aggregate --period weekly --date <date>`) supports backfill and testing.

### 3.5 Backfill

On first deployment (or when onboarding a company with existing git history), a backfill command computes all historical aggregates from whatever daily snapshots exist:

```
govproxy aggregate backfill --from <date> --to <date>
```

Default backfill depth is 12 months (configurable via `--from`), which keeps the first backfill fast and the trend data relevant. This matters for your dogfood: once Phase 1 has pulled WMG's git history, backfill produces the trend history immediately rather than waiting weeks for it to accumulate forward.

## 4. The AI Maturity Score

A composite 0–100 score tracked over time, giving leadership a single number for "how mature is our AI adoption." Computed per team per period.

### 4.1 Tier-Aware Composition

At launch (git-only), the maturity score is computed from git-derived signals and **labeled clearly as a git-based estimate**. As tool connectors come online, the same score incorporates direct-usage components and the label upgrades. The score formula is designed so that components simply switch from "inferred" to "measured" without the number's meaning changing.

**Git-only composition (launch):**

```
maturity (git-based estimate) =
    0.30 * adoption_breadth      // % of team with meaningful AI signal
  + 0.25 * adoption_consistency  // active days / possible days, team avg
  + 0.20 * output_health         // PR throughput trend (positive = good)
  + 0.15 * churn_quality         // inverse of churn (low churn = better)
  + 0.10 * cost_efficiency       // cost-per-PR vs org-average benchmark (lower = better)
```

**Full composition (once tool data exists):** adoption_breadth and consistency get measured directly from tool usage rather than inferred from git, and an acceptance_rate component is added. The weights rebalance, but the 0–100 scale and interpretation stay stable.

### 4.2 Honesty Requirements

- Every display of the maturity score at launch carries a "git-based estimate" label and the MEDIUM-tier confidence marker.
- The score's basis (which components were inferred vs measured) is available on hover/expand.
- Trend matters more than absolute value — "maturity rose from 48 to 61 over the quarter" is the useful statement, not "our maturity is exactly 61."
- The summaries describe the score's movement and basis honestly, never implying measured usage where it was inferred.

### 4.3 Why Compute It Now Rather Than Defer

Computing it now (your choice) means you get trend history from day one, and when tool data arrives the score strengthens rather than appearing from nothing. The clear git-based-estimate labeling keeps it honest in the meantime. This is the right call as long as the labeling discipline holds.

## 5. AI-Generated Summaries

### 5.1 The Four Levels

| Level | Audience | Cadence | Length | Default model |
|---|---|---|---|---|
| Weekly | Team manager | Every Monday | ~2 short paragraphs | local |
| Monthly | Department head | 1st of month | ~1 page | local (configurable up) |
| Quarterly | VP / leadership | Quarter start | ~2–3 pages | local (configurable up) |
| Yearly | Board / annual review | Jan 1 | Full narrative | local (configurable up) |

All default to a local model (Ollama) for privacy. The model is configurable per level — a team can point monthly/quarterly/yearly at a stronger model (Haiku, Sonnet) for higher narrative quality while keeping weekly local, or keep everything local. Configuration mirrors the Phase 1 model-client pattern.

### 5.2 What Goes Into the Model (and What Doesn't)

The model receives **only aggregate numerical data** — never code, never commit contents, never prompt content. A summary input looks like:

```
Period: 2026-W21 (May 19–25)
Team: backend (6 developers, all git-based/MEDIUM tier)
Active developers: 5 of 6
Total commits: 142 (+18% vs prior week)
PRs merged: 23 (+9%)
Avg code churn: 11% (-3 points)
Avg AI signature (est.): 68 (+4)
Subscription cost: $180
Cost per PR: $7.83 (-12%)
Data basis: git analysis + expense data; no direct tool usage available
Notable: developer M.K. inactive 5 days; one new developer started this week
```

The model turns that into readable narrative. Because the input is pure numbers and flags, there's zero privacy exposure and the local model handles it easily.

### 5.3 Tier-Aware Prompting

This is the critical Phase 3 discipline. The summary prompts must instruct the model to:
- Describe git-derived signals as such ("commit activity," "output," "estimated AI signature") and NOT invent usage language ("acceptance rate," "interactions") that isn't in the data
- Carry the confidence basis into the narrative ("based on git activity, since direct tool usage isn't yet connected")
- Frame everything as review/insight, never as judgment of individuals
- Respect the same privacy posture as the dashboard (aggregate framing, no singling out for criticism)

The prompt templates include the data basis explicitly so the model can't drift into describing data that doesn't exist.

### 5.4 Example Outputs (git-only, launch)

**Weekly (team manager):**
> "The backend team had a strong week: 5 of 6 developers were active, with commit activity up 18% and 23 PRs merged. Code churn dropped 3 points to 11%, suggesting cleaner first-pass work. The estimated AI-assistance signal rose slightly. One developer (M.K.) showed no activity for five days — worth a check-in. Cost per merged PR improved 12% to $7.83. Note: these figures are based on git activity and expense data, since direct tool usage isn't yet connected."

**Monthly (department head):**
> "May 2026 across 4 teams (22 developers, all currently git-tracked): output rose steadily, with merged PRs up 14% month-over-month and average churn down to 10%. The git-based AI maturity estimate climbed from 48 to 56, indicating broadening and more consistent AI-assisted activity. Total AI spend was $4,820; cost per PR improved 9%. The frontend team showed the strongest output trend. Two developers remained inactive across the month despite active seats — candidates for the waste review. As the new AI usage strategy rolls out and tool connectors come online, these estimates will be replaced by direct usage measurement."

### 5.5 Regeneration & Storage

- Summaries stored in the `summaries` table (already in V1 schema) with the generated text, model used, period, scope, and a hash of the input data
- If a manager wants a different emphasis, they can regenerate (e.g., "regenerate with focus on cost") — increments a regeneration counter
- If late data arrives and the aggregate changes, the input-hash mismatch flags the summary as potentially stale, offering regeneration
- Summaries are viewable in the dashboard (the summaries API + UI from the design) and exportable

## 6. Technical Design

### 6.1 New/Extended Components

```
src/aggregation/
├── daily.ts          (Phase 1) — assembles daily snapshots
├── weekly.ts         — weekly rollup job
├── monthly.ts        — monthly rollup job
├── quarterly.ts      — quarterly rollup job
├── yearly.ts         — yearly rollup job
├── deltas.ts         — period-over-period delta computation
├── maturity.ts       — tier-aware AI maturity score
├── backfill.ts       — historical backfill command
└── scheduler.ts      — cron orchestration

src/summaries/
├── generator.ts      — orchestrates summary generation
├── prompts.ts        — tier-aware prompt templates per level
├── model-client.ts   — configurable model endpoint (local default)
├── input-builder.ts  — assembles aggregate data into model input
└── staleness.ts      — detects when an aggregate changed after summary generation
```

### 6.2 Schema Additions

```sql
-- Yearly aggregates (new — weekly/monthly/quarterly already in V1 schema)
CREATE TABLE yearly_aggregates (
  id TEXT PRIMARY KEY,
  team TEXT NOT NULL,
  year TEXT NOT NULL,                  -- YYYY
  developer_count INTEGER,
  active_developer_count INTEGER,
  utilization_rate REAL,
  total_subscription_cost REAL,
  total_commits INTEGER,
  total_prs_merged INTEGER,
  avg_code_churn REAL,
  avg_ai_signature_score REAL,
  cost_per_pr REAL,
  ai_maturity_score REAL,
  ai_maturity_basis TEXT,              -- 'git_estimate' | 'mixed' | 'measured'
  utilization_rate_delta REAL,
  maturity_score_delta REAL,
  computed_at TEXT NOT NULL,
  UNIQUE(team, year)
);

-- Add maturity basis + tier columns to existing aggregate tables
ALTER TABLE weekly_aggregates  ADD COLUMN ai_maturity_score REAL;
ALTER TABLE weekly_aggregates  ADD COLUMN ai_maturity_basis TEXT;
ALTER TABLE weekly_aggregates  ADD COLUMN data_quality TEXT;
-- (same for monthly_aggregates, quarterly_aggregates)

-- The summaries table already exists in V1 schema; Phase 3 adds:
ALTER TABLE summaries ADD COLUMN input_hash TEXT;     -- staleness detection
ALTER TABLE summaries ADD COLUMN is_stale INTEGER DEFAULT 0;
```

### 6.3 New CLI Commands

```bash
govproxy aggregate --period weekly --date 2026-05-19   # compute one period
govproxy aggregate backfill --from 2026-01-01 --to 2026-05-25
govproxy summary generate --level weekly --period 2026-W21 --scope team:backend
govproxy summary generate --level monthly --period 2026-05 --scope org
govproxy summary show --level monthly --period 2026-05 --scope org
```

### 6.4 New API Endpoints

```
GET /api/aggregates/:scope/:level?period=   — pre-computed aggregate for a period
GET /api/maturity/:team/trend?range=         — maturity score over time
GET /api/summaries?level=&scope=             — list summaries
GET /api/summaries/:id                       — one summary's text
POST /api/summaries/:id/regenerate           — regenerate (optional focus param)
```

## 7. Resolved Design Decisions

All open questions resolved. Recorded here for reference.

**1. Summary auto-generation.** Weekly and monthly summaries auto-generate on schedule (waiting in the dashboard when the manager arrives). Quarterly and yearly are on-demand — a manager generates them when needed and will typically review/tweak before sharing upward. (Affects task 3.10.)

**2. Maturity score benchmark.** The cost_efficiency component benchmarks each team against the org average for now. Real cross-company anonymized benchmarks are a later-phase feature (from the product vision), not Phase 3. Internal org-average benchmark is the launch behavior.

**3. Backfill depth.** Initial backfill defaults to 12 months of history, configurable via the backfill command's `--from` date. Keeps the first backfill fast and the trend data relevant. (Affects task 3.5.)

**4. Summary tone/voice.** One well-chosen default voice for Phase 3 — concise, analytical, review-oriented. Configurable tone is a later refinement, not Phase 3 scope.

**5. Local model sizing.** Default to a larger local model for better narrative quality (the summaries are the executive-facing output where quality matters most). The model remains configurable, so smaller/faster or cloud options can be swapped in, but the recommended and documented default is a larger local model. Confirm the specific model against available dogfood infra during task 3.7.

## 9. Phase 3 Milestone (Proposed)

By the end of Phase 3:

- Aggregates are pre-computed at all four levels; the dashboard stays instant on long ranges
- The AI maturity score is tracked over time per team, honestly labeled as a git-based estimate
- A manager opens the dashboard Monday morning to an auto-generated weekly summary describing their team's git-based activity in plain language
- A backfill of WMG's git history produces immediate trend depth rather than waiting weeks
- Summaries run on a local model by default — no code or sensitive data leaves the network
- Everything is tier-aware: nothing implies direct-usage data that doesn't exist yet, and the whole system is ready to strengthen automatically when tool connectors come online
